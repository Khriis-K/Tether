# Ship YOLO26n at 1280×736 input

ADR 0002 split two choices: the MOT17 **benchmark detection set** became YOLO26n at 1280×736, and the **shipped detector** stayed YOLO26n at 640 "until #18 measures speed and accuracy together on TensorRT". #18 has now done that, and #17 has built CUDA frame prep, which was the step holding 1280×736 back.

**Decision:** the shipped detector is **YOLO26n at 1280×736** (`models/yolo26n_1280x736.onnx`, exported by `tools/export_model.py` with no arguments). The spec's speed targets (120+ FPS, P99 under 16 ms, on video files) are now stated for this model, running in the **C++ pipeline with TensorRT, CUDA frame prep and the parallel pipeline**. The benchmark detection set and the shipped detector are now the same model. This amends ADR 0002: its benchmark decision stands, and its "the shipped detector stays YOLO26n at 640" is replaced.

## Evidence

From `docs/benchmarks/model-size.md` (#18). That's TensorRT with the CUDA graph and CPU prep, parallel mode, on the Anti-UAV clip, two rounds per row. MOT17 is all 7 train videos with the default tracker.

| Detector | FPS | P99 ms | Meets both targets | HOTA / IDF1 / ID switches |
|---|---|---|---|---|
| n at 640 (the old default) | 141.80–186.27 | 6.77–9.47 | yes | 32.74 / 37.05 / 541 |
| s at 640 | 149.54–185.11 | 6.99–8.86 | yes | 37.81 / 43.28 / 503 |
| **n at 1280×736** | **124.82–126.18** | **9.17–10.45** | **yes** | **41.55 / 49.33 / 772** |
| s at 1280×736 | 108.89–110.06 | 10.99–11.08 | no (FPS) | 44.86 / 52.30 / 707 |
| m at 640, m at 1280×736 | 105.43–106.05, 46.77–47.20 | 11.17–11.31, 24.46–24.62 | no | 38.72 / 44.70 / 493, 46.90 / 54.77 / 700 |

- **It's the most accurate row that met both targets**: +8.81 HOTA and +12.27 IDF1 over n at 640. Its ID switches are higher (772 against 541) because it finds far more people: detector recall goes from 33.7% to 54.6%. A raw switch count isn't normalized for that, and HOTA and IDF1 are.
- **With CPU prep it cleared 120 FPS by only 4.82–6.18 FPS**, and prep was its slowest stage (busy 99.2–99.3%). #17 then moved prep to the GPU (`docs/benchmarks/cuda-prep.md`). On the same clip in parallel mode, FPS rose from 126.63–127.71 to **195.45–195.86**, with P99 frame time **6.49–6.57 ms**. Capture (video decoding) is now the slowest stage, busy 99.7%. That puts the shipped configuration 75.45–75.86 FPS above the target, and at 1280×736 the input size no longer costs FPS on this clip: the 640 model with CUDA prep runs 193.49–195.18.
- **The MOT17 rows are scored on TensorRT dumps**, the runtime that ships. ONNX Runtime and TensorRT dumps of the same model differ by up to 0.39 HOTA, 0.56 IDF1 and 12–40 ID switches under the same tracker, so gaps smaller than that are noise. The gap that decides this (n at 1280×736 against s at 640, the next most accurate row that met the targets) is 3.73 HOTA.

## Consequences

- **Defaults that mean "the shipped detector" now point at YOLO26n at 1280×736:**
  - `tether-pipeline` with no `--model`: `--model-size n|s|m` now picks `models/yolo26<size>_1280x736.onnx`, the shipped input size, which also fixes `s` and `m` pointing at files the export tool never made.
  - Python's `DEFAULT_MODEL` (`tether.demo`). It's shared by `tether-demo`, `tether-mot17`, `tether-pipeline-compare`, `tether-mode-compare` and `tether-runtime-compare`. Each of these runs or compares "the detector we ship" unless told otherwise, and `tether-pipeline-compare` must give both pipelines the same model as `tether-pipeline`'s default.
  - `tools/export_model.py` with no arguments.
  - `tether-model-compare` takes `--models` explicitly and has no default.
- **The runtime, prep and pipeline defaults don't change**: ONNX Runtime, CPU prep, sequential. They work on any machine, with no GPU and no TensorRT download. The shipped configuration is opt-in, and the docs give its full command:
  ```
  tether-pipeline VIDEO --runtime tensorrt --prep cuda --pipeline parallel
  ```
- **The cost on the default CPU runtime is real.** With ONNX Runtime on the CPU (#16, `docs/benchmarks/tensorrt-runtime.md`, sequential, two rounds each):
  - Detect takes **2.20–2.22× longer** at 1280×736 than at 640 on the Anti-UAV clip (32.77–33.02 → 72.68–72.93 ms), and **2.21–2.29×** on MOT17-04 (33.30–33.33 → 73.66–76.26 ms).
  - Whole-pipeline FPS drops from 24.5–25.2 to 11.9 on the Anti-UAV clip, and from 20.0 to 9.8–10.5 on MOT17-04.
  - The Python demo (`tether-demo`) runs ONNX Runtime too. ADR 0002 timed its prep + inference + decode at 39 ms (640) and 91.9 ms (1280×736) per frame on the CPU.

  On a CPU-only machine, or for a live webcam without TensorRT, pass the 640 model explicitly:
  ```
  python tools/export_model.py --size 640     # models/yolo26n.onnx
  tether-pipeline 0 --model models/yolo26n.onnx
  ```
- **`models/yolo26n.onnx` keeps its name.** It's YOLO26n at 640, the first shipped model, and earlier results and docs refer to it (`results/mot17/detections/yolo26n/`). Every other export is named after its model and size.
- **MOT17 keeps reporting two rows**: the 1280×736 set as the headline, and 640 as the second row, now labelled as the old default rather than the shipped detector.
- **Not re-measured for this change:** `--show`, `--record` and the webcam with the shipped configuration, and MOT17-04, which is JPEG files. MOT17-04 misses both targets for every model (65.46–65.67 FPS with CUDA prep), because JPEG decoding caps it.
